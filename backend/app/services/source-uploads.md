# Private source upload helpers

These are internal building blocks for the upload service. No upload/delete HTTP
route is added. The parser and API owners still validate the upload before using
them. Source files stay in the existing private `financial-documents` bucket.

## Integration order

1. Inject `get_source_upload_access` from `app.services.source_dependencies` using
   FastAPI `Depends`. It authenticates the caller and creates request-local helpers
   with that user's original token and the existing publishable-key HTTP client.
2. Validate form fields, enforce the agreed bound while reading the file, and inspect
   its actual content before reserving anything.
3. Construct `SourceAttempt` on the server using `access.user.id`, validated user /
   document types, a backend-selected workspace name, original filename and kind.
   UUIDs are generated by default. Do not accept owner/attempt IDs from the form.
4. Parse using `attempt.document_id` for source references and validate the result.
   Then call `await access.reservations.reserve(attempt)`. This invokes
   `public.reserve_source_upload` in one database transaction. It derives ownership
   from `auth.uid()`, inserts the workspace/document, and constructs the canonical path.
5. Call `await access.storage.upload(reservation, content, max_bytes=agreed_limit)`.
   The caller must supply the accepted byte limit; this change does not silently
   approve the team's proposed 5 MiB limit. The helper independently checks the
   already-read bytes, but does not replace bounded reading in the route.
6. Use `ParsedDocumentRepository.finalize` through the authenticated dependency in
   `app.db.dependencies` to save parsed JSON and transaction rows together. See
   [parsed persistence](../db/parsed-documents.md). Return 201 only after this and
   the source upload succeed. Use the [recovery service](upload-recovery.md) when
   this attempt fails; the API owner still implements the public orchestration.

The new RPC migration must be reviewed and applied through the team's normal
migration workflow before using this against hosted Supabase. The initial migration
is already applied; do not rerun or rewrite it. This change prepares the new file
locally and does not deploy it automatically.

## Models and paths

`SourceKind` allows CSV/XLSX and chooses a fixed MIME type. It does not inspect
bytes or promise that any particular bank's format can be parsed. Existing
user/document eligibility remains in place; deferred balance-sheet upload behavior
is still a route/product decision, not a new parser in this change.

`SourceAttempt` is frozen after validation. It strips directory components and
control characters from the metadata filename, validates the name/extension/context,
and generates this path without incorporating the original filename:

```text
{user_id}/{workspace_id}/{document_id}/source.csv
{user_id}/{workspace_id}/{document_id}/source.xlsx
```

Filenames still must be rendered as text in the frontend. Filename cleanup is not
HTML escaping. These internal models contain private paths/metadata and must not
be dumped directly into responses or logs.

The repository validates the returned IDs, name, context, path and status before
returning `SourceReservation`. `uploaded` is the existing database enum/default
used while reserving an unparsed document; by itself it does not prove file bytes
have been stored or parsed. No new status value is introduced here.

## Immutability, failure and cleanup

Upload uses the Storage API with `x-upsert: false`. Existing sources are never
replaced automatically. Original caller tokens are sent on every operation; the
helpers do not mutate shared client authentication or use elevated keys.

`await access.storage.remove(attempt)` removes that exact generated object through
the Storage API. It can clean an orphan after metadata loss because the existing
Storage policy authorizes the owner's prefix. It does not delete document/workspace
rows. True means the exact removed object was returned. False means no removed
object was returned; do not use it as proof that storage is empty or authorized.

This is a removal primitive. The [recovery service](upload-recovery.md) now makes
the database decision and coordinates failed state and metadata release around
it. Use that service for upload failures so cleanup cannot discard a confirmed
save. There is no public deletion endpoint or automatic background cleanup.

| Failure | Meaning / caller action |
| --- | --- |
| `SourceUnauthorized` | Token rejected; translate to safe 401 with a Bearer challenge |
| `SourceConflict` | Duplicate ID/object; return a safe conflict, never overwrite or blindly retry |
| `SourceTooLarge` | Reject with 413; respect both the agreed application bound and hosted bucket limits |
| `SourceUnavailable` | Sanitized dependency/permission/configuration failure; translate to a safe 503 |
| `SourceOutcomeUnknown` | A reservation/upload/removal may have committed; retain the same IDs and reconcile before any retry or deletion |
| Invalid internal context (`ValueError`) | Validate inputs at the route boundary; do not expose Pydantic payloads with financial data |

Timeouts, 5xx responses and malformed successful write receipts are uncertain.
No automatic retry, deletion or success is reported in those cases. The caller
has the original attempt UUIDs for a future ownership-scoped reconciliation lookup.
Database metadata and Storage bytes are separate systems: one SQL transaction
cannot roll back an HTTP file upload. Recovery is now available for explicit
reconciliation of the original attempt, rather than blindly retrying a write.

## Verification

- `backend/tests/db/test_source_uploads.py`: RPC contract, receipt validation,
  dependency wiring, two-user tokens and authentication-before-write behavior.
- `backend/tests/services/test_source_storage.py`: paths, validation, bytes/MIME,
  byte bounds, no overwrite, exact removal, safe failures and lost responses.
- `supabase/tests/source_reservations.sql`: real SQL role checks, ownership,
  immutable IDs and rollback of the first insert when the second insert fails.

The original helper tests use synthetic HTTP responses. The follow-up
[component and SQL runner](../../../supabase/tests/README.md) now joins the actual
Python helpers to the real migrations/RLS in embedded PostgreSQL. This checks
reservation, save, reads and recovery without hosted changes. Auth/Storage HTTP
responses and bytes are synthetic. It does not replace real Storage API testing,
full Docker Supabase replay or the live two-user API/parser/browser demonstration.
