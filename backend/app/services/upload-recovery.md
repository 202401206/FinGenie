# Recovering an interrupted bank-statement upload

`UploadRecoveryService.recover(attempt, parsed_data)` settles one failed attempt
using the verified caller's token. It is an internal helper for Anshuman's upload
service. It adds no public route, parser, background worker or automatic retry.

## When to call it

Keep the existing order: authenticate, generate `SourceAttempt`, validate/parse
the bounded file, reserve metadata, upload the source, then finalize parsed data.
Validate the complete parsed result, including JSON-serializable extra fields,
before reserving anything. A parse failure before reservation needs no cleanup.

Inject `get_upload_recovery_service` from `source_dependencies.py` with FastAPI
`Depends`. After the original workflow stops on a reservation, upload or save
failure, call:

```python
result = await recovery.recover(attempt, parsed_data)
```

Keep the original server-generated IDs, extension and parsed result. Do not
reparse with new IDs, accept recovery IDs from an untrusted request, or start
another save while recovering this attempt. The parsed input follows the same
validation and exact Decimal serialization as `ParsedDocumentRepository`.
Invalid internal input still raises `ParsedDocumentRejected`/`ValueError`;
recovery does not hide a programming error as successful cleanup.

| Result | Meaning | Upload service action |
| --- | --- | --- |
| `completed` + receipt | Matching saved JSON, metadata and transaction rows were found, and the source is registered | Use the confirmed save receipt in the normal success response |
| `cleaned` | The attempt was cancelled, its source metadata is absent after Storage removal, and its document/workspace were released | Return the original safe upload failure, never upload success |
| `pending`, `auth_required` | The user's credentials were rejected | Re-authenticate; retain the attempt context for a later explicit check |
| `pending`, `reconciliation_required` | The initial database decision could not be confirmed | Report a dependency failure; retain context and do not delete anything blindly |
| `pending`, `cleanup_required` | The attempt was cancelled but removal/release was not confirmed | Report cleanup pending; retain context and retry recovery explicitly when the dependency works |
| `pending`, `state_conflict` | Existing data differs from the expected save or is unsafe to discard | Preserve it and investigate; do not overwrite or auto-delete |

These are internal results, not a new public HTTP response contract. Routes must
translate them with the agreed API schemas and safe errors. A pending result is
never proof of rollback. Do not return tokens, parsed financial content, private
paths, raw SQL failures or this internal attempt model to clients/logs.

## Why the steps are ordered this way

1. `begin_upload_recovery` derives the owner from `auth.uid()`, takes the shared
   transaction advisory lock, and locks the owned rows. A completed save must match
   the full expected JSON, currency/period, transaction count and transaction
   multiset, with its registered source still present. It is returned unchanged.
2. An unparsed attempt with no transaction rows is cancelled and marked `failed`.
   An absent reservation is also cancelled, so a queued request cannot create it
   after the absence check. Unexpected partial/saved state returns a conflict.
3. The service removes only the canonical source through the Storage API. An empty
   removal receipt alone does not establish that the file is gone.
4. `release_failed_upload` takes the same lock, checks the cancellation record and
   source metadata absence, then deletes only the failed document and empty
   workspace in one transaction. The cancellation record remains.

The `upload_cancellations` table stores only owner/workspace/document UUIDs and a
timestamp. Owner RLS permits select/insert, with no ordinary update/delete grant.
It blocks late reservation, Storage insertion and finalization, even after the
workspace is deleted. Advisory locks serialize cooperating transactions; they
alone would not remember cancellation after a request finishes. Do not remove
these records on a timer without designing and reviewing a safe retention policy.
Their current foreign key also restricts deleting an Auth user until account
cleanup is handled explicitly.

`EXCEPT ALL` checks transaction values as a multiset, so legitimate duplicate
rows remain meaningful. Equal row counts alone would miss changed amounts. JSON
object key order is irrelevant under JSONB equality; array order still matters.

## Migration and access rules

Review/apply migrations in their existing order before live use. The new file is
`20261101190235_upload_recovery.sql`, generated by the pinned Supabase CLI. Its
timestamp comes from that CLI. Earlier migration files are unchanged.

It adds cancellation RLS, the recovery functions and a shared lock helper. It also
replaces the reservation/finalization function definitions with the same signatures
and existing behavior plus the cancellation guard. The Storage INSERT policy now
checks the same guard and requires an owned, pending document. Existing owned
reads/deletes and the no-overwrite behavior are retained. Functions use security
invoker, an empty search path and authenticated-only execute grants.

PostgreSQL cannot roll back an HTTP file operation. The source check inspects
Storage metadata, not the physical bytes. Cooperating workflow writers use the
same lock and cancellation checks; direct owner SQL edits, independent authorized
file deletion and account-retention workflows are outside this coordination.
This is not immutable archival storage or a distributed transaction.

## Verification and remaining integration

See [the repeatable test commands](../../../supabase/tests/README.md). Unit tests
check call order, original user tokens, exact JSON, receipt validation and safe
failure handling. Component tests run the real Python helpers against the real
migrations/RLS in embedded PostgreSQL. Auth responses and Storage HTTP/bytes are
synthetic; the SQL runner's minimal auth/storage schema is test-only.

The tests cover happy-path persistence/reads, user separation, lost successful
reservation/upload/finalization responses, failed removal, repeated recovery,
lost cleanup responses and preservation of changed saved data. SQL tests also
check late writes, anonymous rejection and cancellation permissions.

They do not exercise the real parser, public upload routes, a browser, hosted
Storage, full Docker Supabase or simultaneous independent PostgreSQL sessions.
Anshuman and Dhaval still need to connect their parts and run the live two-user
upload/read/failure demo together. No hosted migration was applied by this change.
Recovery is request-driven: surviving a backend restart requires the caller/team
to retain enough attempt context securely. There is no durable job queue here.
